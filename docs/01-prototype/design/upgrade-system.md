# Upgrade System Design

Upgrades are items that change how the player or the game plays by applying permanent or temporary effects.

The upgrade system builds on the existing item, kit, shop, progression, and effect systems rather than introducing an attribute upgrade system.

Upgrades can target the player, the ball, venue, or partner.

## Upgrade

An upgrade is represented by an item that applies one or more effects. The item is owned by the player and is managed through the kit/item system.

Effects can be permanent or temporary and can modify stats or behaviour. The existing effect system is responsible for evaluating and applying these effects.

Examples of things an upgrade could affect include:

* Paddle speed
* Paddle power
* Paddle size
* Ball speed
* Ball behaviour
* Venue behaviour
* Partner behaviour

The item itself must be owned and placed in the player's kit. The effect system represents what the item does.

This keeps the distinction between:

* **Item** - something the player owns
* **Kit** - the collection of items the player owns
* **Active item** - an item currently equipped or otherwise active
* **Inactive item** - an item currently stored in the GearRack or BallRack or otherwise inactive generating passive Friendship
* **Effect** - the change produced by an item
* **Upgrade** - an item whose purpose is to provide an effect

## Obtaining Upgrades

Upgrades are obtained through the shop.

When an item is purchased, it becomes part of the player's kit.

The shop already uses a rotating selection of items. The selection is not random and can change based on progression and other factors.

The upgrade system therefore does not need to decide how items appear in the shop. The shop is responsible for offering and selling items; the item and kit systems are responsible for ownership.

The basic flow is:

```text
Shop
  ↓
Purchase item
  ↓
Item added to Kit
  ↓
Player equips item
  ↓
Item becomes active
  ↓
Effect is evaluated
  ↓
Effect changes player/game behaviour
```

             │     Shop     │

                    │ Purchase

## Kit

The kit represents every item owned by the player.

The kit has a capacity. The capacity determines the maximum number of items the player can own.

Kit capacity increases through player progression.

The kit contains both active and inactive items.

Active items are equipped and their effects are running.

Inactive items remain owned by the player but are not currently equipped and are stored in the appropriate inactive storage area. An inactive item may generate passive Friendship.

The passive Friendship generated by an inactive item scales with the item's cost and level.

```text
Kit
├── Active items
│   └── Effects are running
│
└── Inactive items
    └── Generate passive Friendship
```

## Equipping

An item becomes active when it is equipped by the player.

The existing item UI represents items as physical objects that can be dragged between slots.

When an item is equipped:

1. The item moves into an active slot.
2. The item becomes active.
3. Its effects become available to the effect system.
4. The effect system evaluates the effect and applies the resulting outcome.

When an item is moved back into an inactive slot, its active effect is no longer running and it instead contributes to passive Friendship.


## Kit Capacity

The player cannot exceed the current kit capacity.

If purchasing or accepting an item would exceed the available capacity, the player refuses the item with the existing refusal animation.

Kit capacity grows with player progression.

Meaning progression indirectly increases the number of upgrades the player can own.

## Active and Inactive Items

Items have two important runtime states:

### Active

An active item is equipped by the player.

Its effects are running and can modify the game.

### Inactive

An inactive item is still owned but is not equipped.

Inactive items generate passive Friendship.

The passive Friendship rate scales with:

* Item cost
* Item level

This creates a trade-off between equipping an item for its gameplay effect and keeping it inactive for passive Friendship.

## Effects

Upgrades use the existing effect system.

An effect consists of a trigger, optional conditions, and an outcome.

The upgrade system should not duplicate this logic.

Instead, an item provides its effect definition and the existing effect system evaluates it.

Effects can have level scaling.

Percentage modifiers should be used where appropriate to prevent stacking from producing exponential growth.

For example, multiple sources of Ball Speed should combine through the existing modifier/evaluation rules rather than each modifier multiplying the result of the previous modifier.

```text
Item
  ↓
Effect
  ↓
Trigger / Conditions
  ↓
Outcome
  ↓
Modified stat or behaviour
```

## Scaling

The strength of an upgrade can scale with the item's:

* Cost
* Level

Progression may also influence scaling where appropriate.

The exact scaling formula belongs to the effect system rather than the item itself where possible.

This allows different effects to use the same general item/effect model without creating upgrade-specific calculation logic.

## Stacking

Some items can stack.

Stacking allows multiple items or copies of an item to contribute to the same outcome.

For example:

```text
Ball Speed Item
+5% Ball Speed

Ball Speed Item
+5% Ball Speed

Total
+10% Ball Speed
```

The existing effect evaluation rules should determine how multiple modifiers combine.

Percentage modifiers should prevent stacking from producing exponential growth.

Whether every item can stack, or whether stacking is explicitly defined per item, remains an open design decision.

## Duplicate Items

The system should support the possibility of multiple copies of an item.

However, it is not yet decided whether all items can be owned more than once.

There are potentially two categories:

### Unique items

A unique item can only exist once in the player's kit.

For example, a named piece of equipment may represent a single object.

### Stackable items

A stackable item can be purchased or obtained multiple times.

Multiple copies contribute their effects according to the effect system's stacking rules.

The item definition should therefore be able to communicate whether an item is unique or stackable rather than making this a global assumption.

## Synergy items

Some items can be paired together to create a synergy.

A synergy may provide a combined effect when the required items are owned or active.

Synergies can also influence the shop. When a player owns a max-level item that has a defined synergy partner, the partnered item receives an increased probability of appearing in the shop rotation for three shop cycles.

The exact synergy effect and shop weighting are defined by the item/synergy data rather than by the upgrade system itself.

## Removing Items

Items remain part of the kit until they are removed.

The Tinkerer can destroy items.

Destroying an item removes it from the player's kit and therefore removes its ownership.

If multiple copies of the same item exist, destroying one copy should only remove that particular item.

If the item is available in the shop again, the player can potentially purchase another copy.


## Relationship With Progression

Progression affects upgrades in several ways.

Player progression can:

* Increase kit capacity
* Unlock new items or shop availability
* Potentially influence item/effect scaling
* Change the rotating shop selection

The upgrade system should acknowledge progression information rather than becoming responsible for progression itself.

Progression remains responsible for determining when new progression milestones or unlocks occur.

## Player-facing upgrades

The initial implementation should focus on upgrades that affect the player's gameplay.

The most obvious targets are the player's paddle and the ball.

Examples include:

* Paddle speed
* Paddle power
* Paddle size
* Ball speed
* Ball-related behaviour
* Other player-facing gameplay modifiers

This provides a focused MVP while exercising the complete upgrade lifecycle:

```text
Purchase
→ Own
→ Equip
→ Activate effect
→ Play
→ Unequip / replace / destroy
```

## Upgrade Targets

The effect system already allows outcomes to affect more than the player.

Future upgrades could affect:

* Ball
* Paddle
* Court / venue
* Partner

This means the distinction should remain:

> An upgrade is an item that provides an effect.

rather than:

> An upgrade is a player-stat modifier.

The latter would unnecessarily restrict the system and the desired narrative brought by the items.

## Example Upgrades

### Faster Paddle

An equipped item increases paddle movement speed.

### Powerful Paddle

An equipped item increases paddle power.

### Fast Ball

An equipped item increases ball speed.

### Soul Collector

An item increases the player's Soul multiplier.

An upgrade that affects progression/economy rather than direct movement.

### Friendship objects

An inactive item generates additional passive Friendship.

An upgrade that affects progression/economy rather than direct movement.

## Design Principles

### Use the existing systems

Upgrades should use the existing:

* Item system
* Kit system
* Shop system
* Effect system
* Progression system

A separate `UpgradeManager` should not be introduced unless implementation reveals a genuine responsibility that cannot naturally belong to these systems.

### Player-first, not player-only

The first upgrade implementation should focus on player upgrades.

However, the architecture should not prevent effects from targeting the ball, venue, or partner.

### Data-driven upgrades

An upgrade should preferably be represented by item data/resources rather than hard-coded upgrade behaviour.

This allows new upgrades to be added by creating items and effects instead of implementing new upgrade-specific systems.

## MVP Scope

The first upgrade prototype should demonstrate:

* Purchasing an upgrade from the shop
* Adding the item to the kit
* Respecting kit capacity
* Equipping the item
* Activating its effect
* Seeing the effect modify player gameplay
* Unequipping the item
* Returning it to an inactive state
* Generating passive Friendship while inactive
* Loading the item back into the kit
* Supporting at least one stacking example

Partner and venue upgrades do not need to be implemented as part of the first prototype, but the design should not prevent them from being added later.

## Open Design Decisions

The following decisions need confirmation before implementation is considered final:

* Are all items unique, or can some/all items be purchased multiple times?
* Is stackability defined per item?
* Does every duplicate occupy a separate kit slot, or can identical items form a stack?
* Can active items be replaced directly when the kit is full?
* Are consumable items part of the initial upgrade system?
* What determines an item's level?
* Can the player upgrade an item's level independently from progression?
* Does progression directly affect effect strength, or only item availability and kit capacity?
* Should inactive passive Friendship be generated by every item or only specific items?
* Can an item have both an active gameplay effect and an inactive passive effect?
* Which player stats should be included in the first prototype?
* Should the first prototype include ball effects, or focus exclusively on paddle/player effects?
* How should unique items behave when they are destroyed and later become available in the shop?
* Should partner-affecting upgrades be considered part of the long-term upgrade system or remain a separate future mechanic?

## Proposed Prototype

The smallest useful prototype would be three items:

1. **One unique player upgrade**

   * Modifies paddle speed or power.
   * Demonstrates a permanent stat modifier.

2. **One stackable upgrade**

   * Modifies ball speed.
   * Demonstrates multiple copies and percentage stacking.

3. **One passive/inactive upgrade**

   * Generates additional Friendship while inactive.
   * Demonstrates the active/inactive trade-off.

Together these three items exercise the majority of the proposed system without requiring a large catalogue.

## Summary

The upgrade system does not need to introduce a new ownership or effect architecture.

An upgrade is an item in the player's kit that provides one or more effects.

The shop controls acquisition, the kit controls ownership and capacity, item state determines whether the item is active or inactive, the effect system controls how its effects are evaluated, progression controls unlocks and capacity growth, and the save system persists the player's owned items.

The initial focus should be player upgrades, but upgrades should remain capable of targeting other systems through the existing effect architecture.

The primary remaining product decisions are around item uniqueness, stacking, kit capacity, consumables, item levels, scaling, synergies, and the exact scope of the first player-facing upgrade prototype.
